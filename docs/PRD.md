## 1. 项目背景

### 1.1 背景与问题

哔哩哔哩（B站）存在大量由UP主持续发布的视频内容。由于UP主主动删除、修改可见范围、版权限制、平台处理等原因，部分历史投稿可能不再能够正常访问。

目前用户主要面临以下问题：

1. **缺少历史记录**：无法方便地查询某个UP主曾经发布过哪些视频。
2. **视频变化不透明**：很难知道某个视频从什么时候开始无法访问。
3. **人工跟踪成本高**：需要反复打开UP主空间检查投稿情况。
4. **私人备份不及时**：用户电脑不在线时，无法执行本地备份，可能错过视频仍然可访问的时间。
5. **订阅与备份缺少联动**：公共信息跟踪和用户私人备份通常由不同工具完成。

### 1.2 产品定位

本项目定位为：

**面向B站内容的公共历史状态追踪与个人本地备份管理平台。**

系统由两个相互独立但协同工作的部分构成：

- **公共服务端**：管理用户订阅，聚合监控目标，追踪视频状态，记录历史元数据，向用户推送变化事件。
- **本地 Agent**：在用户控制的设备上运行，使用用户自己的授权凭据，对具备合法保存权限的内容执行本地备份。

公共服务端不存储、不转发视频文件，也不向公众提供历史视频播放或下载服务。

### 1.3 产品目标

- 为用户提供统一的UP主及视频订阅入口。
- 在合法数据来源允许的情况下，对多个用户订阅的目标进行统一、持续、去重监控。
- 记录视频首次发现、元数据变更及可访问性变化。
- 即使所有本地 Agent 离线，服务器也能够独立维护公共监控记录。
- Agent 重新上线后能够同步离线期间发生的事件。
- 降低个人用户管理备份任务的复杂度。
- 在系统架构层面隔离公共数据与私人视频文件。

### 1.4 非目标

本项目第一版不计划实现：

- 公共视频托管、点播、分享或下载服务。
- 下架视频的重新上传和传播。
- 绕过会员、付费、DRM、登录权限或平台访问限制。
- 视频内容推荐算法。
- 用户之间的P2P视频分享。
- 分布式视频存储网络。
- 全站视频索引或无订阅目标的大规模扫描。

## 2. 用户角色

### 2.1 访客

无需登录，可以查询允许公开展示的UP主历史投稿、视频状态和历史变化记录。

### 2.2 注册用户

可以订阅UP主或单个视频，管理订阅列表、接收通知、设置个人隐私偏好，并绑定本地 Agent。

### 2.3 Agent 用户

已绑定本地设备的注册用户，可以配置本地备份策略、存储位置、任务并发和文件管理选项。

### 2.4 系统管理员

负责监控公共服务健康状态、管理数据源、处理投诉与删除请求、管理异常任务和审查系统运行日志。

## 3. 核心业务规则

**BR-01：订阅与监控分离**

用户订阅关系为私人用户数据，公共监控任务为共享系统资源。

同一UP主被多个用户订阅时，服务端应尽可能复用监控任务，避免不必要的重复请求。

**BR-02：服务器与Agent独立运行**

公共监控服务不依赖用户的Agent在线。

本地Agent离线时，服务器继续记录有权监测的视频状态，但不替用户执行视频备份。

**BR-03：公共服务器不存储视频**

服务器不接收或保存视频媒体文件、分片、视频播放缓存以及本地备份文件。

**BR-04：数据获取需要合法授权**

任何真实监控与备份功能，都必须遵循适用法律、平台协议和数据源授权范围。

无权限访问或使用的数据，不得通过绕过限制的方式获取。

**BR-05：区分观察结果和事实判断**

“视频不可访问”不等于“视频已被删除”，更不等于“视频被平台下架”。

系统只展示具有证据支持的观测状态，不推断无法确定的删除原因。

**BR-06：历史记录不保证完整**

系统只能记录开始监控后，或者从合法历史数据源获得的信息。

首次监控前已经消失的视频，可能无法被发现。

**BR-07：事件持久化与幂等处理**

视频变化事件应具有唯一标识，并支持Agent断线恢复、重复拉取和幂等处理。

## 4. 功能需求

功能优先级定义：

- **P0**：MVP必须实现。
- **P1**：核心闭环完成后的增强功能。
- **P2**：后续扩展功能。

### 4.1 用户及账户模块

**FR-001：用户注册与登录（P0）**

用户能够创建平台账户、登录和退出。

验收标准：
- 未登录用户不能修改订阅关系。
- 账户只能操作自身的私人订阅和设备。
- 登录状态过期后，受保护接口拒绝访问。

**FR-002：个人订阅管理（P0）**

用户可以通过UP主UID或视频BV号添加订阅，也可以取消订阅。

验收标准：
- 同一用户重复订阅同一目标，不产生重复订阅记录。
- 取消某项订阅后，不再收到该订阅产生的新通知。
- 订阅关系默认不公开。
- 添加无效标识时，返回明确错误。

**FR-003：订阅偏好（P1）**

用户可以针对不同UP主或视频分别配置通知及本地备份策略。

### 4.2 公共监控模块

**FR-004：监控目标聚合（P0）**

服务端汇总所有用户订阅的UP主及视频，维护统一的监控目标集合。

验收标准：
- 多个用户订阅同一UP主，默认只生成一个对应的UP主监控目标。
- 用户之间的订阅数据保持隔离。
- 最后一个订阅者取消后，目标可以停止主动监控，具体清理策略由后续设计确定。

**FR-005：UP主投稿发现（P0）**

对获得合法数据访问权限的UP主，定期获取允许访问的投稿信息，并将新视频加入历史索引。

系统至少记录：
- UP主UID
- 视频BV号
- 视频标题
- 原始投稿时间
- 系统首次发现时间
- 数据来源和观测时间

系统还可根据数据来源许可记录简介、分P结构及统计数据等非媒体信息。

**FR-006：视频可访问性监控（P0）**

定期检查已记录视频的可访问状态。

建议支持以下状态：

| 状态 | 含义 |
|---|---|
| UNKNOWN | 尚无可靠判断 |
| AVAILABLE | 已确认当前可访问 |
| SUSPECTED_UNAVAILABLE | 疑似不可访问，尚待确认 |
| CONFIRMED_UNAVAILABLE | 经多次有效检查，确认当前无法正常访问 |
| ACCESS_RESTRICTED | 受到权限或地区等访问条件限制 |
| CHECK_FAILED | 本次检查失败，结果不可信 |

如果历史异常的视频恢复正常访问，应当记录恢复事件。

验收标准：
- 网络超时或接口故障不会直接产生“已删除”结论。
- 可配置重试、确认次数及检查间隔。
- 系统记录最后一次成功检查和首次发现异常的时间。
- 保留能说明状态判断依据的非敏感证据。

**FR-007：历史元数据版本管理（P1）**

当视频标题、简介等允许记录的字段发生变化时，生成历史版本或字段变更记录。

只在实际变化时保存必要的增量或快照，避免重复保存大量相同内容。

**FR-008：公共历史查询（P0）**

访客和注册用户可按照UP主UID、视频BV号查询已有的公开历史索引。

展示内容包括：
- 视频基本信息
- 当前观测状态
- 首次发现时间
- 最后确认正常时间
- 首次发现异常时间
- 主要历史状态事件

搜索与展示需要明确区分真实观测数据和未知数据。

### 4.3 事件与通知模块

**FR-009：视频事件日志（P0）**

当监控目标出现有意义的变化时，服务器产生持久化事件。

事件类型包括：
- VIDEO_DISCOVERED：发现新投稿
- VIDEO_METADATA_CHANGED：视频元数据变更
- VIDEO_UNAVAILABLE：确认视频不可访问
- VIDEO_RECOVERED：视频恢复访问
- VIDEO_ACCESS_RESTRICTED：访问权限变化

每个事件至少包含事件ID、目标标识、事件类型、观测时间及必要的变更信息。

**FR-010：订阅事件通知（P0）**

服务器按订阅关系将相关事件分发给注册用户。

MVP阶段支持站内通知；邮件、Web Push等作为后续增强。

重复观测不得持续产生相同的通知。

**FR-011：Agent增量同步（P0）**

Agent使用服务端同步游标获取未处理事件。

验收标准：
- 断线后能从已确认游标继续拉取。
- 事件重复下发不会造成重复任务。
- 只有完成本地事务性持久化后才能推进同步游标。
- 用户无权访问其他用户的私人事件。
- 游标过期或历史事件已清理时，支持重新获取状态快照并恢复同步。

### 4.4 本地Agent模块

**FR-012：Agent设备绑定（P0）**

用户可以登录公共网站并绑定自己的Agent设备。

设备应拥有独立的身份凭据，用户可查看、撤销和重新绑定设备。

**FR-013：本地备份任务管理（P0，受授权条件约束）**

Agent可以根据用户选择的策略，对具备合法复制权限且当前可获取的内容创建本地备份任务。

备份规则包括：
- 仅备份新增视频。
- 备份允许访问的历史视频及新增视频。
- 仅接收通知，手动选择备份。
- 完全关闭备份。

验收标准：
- Agent离线时不会假装备份成功。
- 用户可暂停、恢复和取消本地任务。
- 对已备份的视频进行去重。
- 备份失败时记录可理解的错误。
- 视频不可访问或权限不足时，不绕过访问限制。

**FR-014：本地文件管理（P0）**

备份文件保存到用户指定目录，相关状态记录存储在本地数据库中。

允许记录文件路径、备份时间、文件大小、任务状态及可选校验信息。

**FR-015：本地敏感凭据管理（P0）**

若使用用户B站账号，相关认证信息只能保存在用户设备上，不得同步至公共服务器。

优先使用官方允许的认证方式和操作系统安全凭据存储。

服务端不得通过Agent执行任意系统命令。

**FR-016：离线事件补偿（P0）**

Agent恢复在线后：
1. 同步服务器记录的新事件。
2. 更新本地任务与视频状态。
3. 按用户规则判断哪些内容需要备份。
4. 检查当前是否具备合法访问和保存条件。
5. 执行可行任务，将不可完成的任务标记为失败或不可访问。

系统不保证补齐离线期间已经消失的视频文件。

### 4.5 管理与合规模块

**FR-017：监控任务管理（P0）**

管理员能够查看监控任务数量、执行状态、最近成功时间、错误原因和数据源健康情况。

**FR-018：投诉、纠错及删除处理（P0，上线前必备）**

提供公共信息纠错、隐私投诉、侵权投诉和数据删除申请渠道。

依据适用规则处理请求，并记录处理结果。

**FR-019：评论历史功能（P2）**

评论内容的历史归档属于潜在扩展功能，不纳入MVP。

在完成个人信息、著作权、平台授权和数据最小化评估前，不对评论正文实施批量公开归档。

## 5. 核心业务流程

### 5.1 用户订阅UP主

1. 用户登录网站。
2. 输入目标UP主UID。
3. 系统验证输入及是否具有合法数据访问方式。
4. 系统创建用户订阅关系。
5. 若公共监控任务已存在，直接复用。
6. 若目标尚未监控且满足数据来源条件，创建监控任务。
7. 系统展示当前已知投稿与历史事件。

### 5.2 服务器发现新视频

1. 监控任务按照数据源许可的频率执行。
2. 获取目标UP主允许访问的视频元数据。
3. 将本次结果与历史记录比较。
4. 若发现新视频，写入视频索引。
5. 产生新视频事件。
6. 通知对应订阅用户。
7. 在线Agent增量同步并按自身规则处理。

### 5.3 服务器发现视频异常

1. 某个视频本次检查无法访问。
2. 系统保存观测结果，并判断是否需要重新确认。
3. 在缺少充分证据时，标记为疑似异常。
4. 多次有效检查满足规则后，记录确认不可访问事件。
5. 公共页面展示最后确认正常时间和首次异常时间。
6. 向相关订阅用户发送状态变化通知。

### 5.4 Agent离线与恢复

1. Agent离线，公共监控服务照常运行。
2. 服务端持续生成并保存视频变化事件。
3. 用户重新启动Agent。
4. Agent从自身同步游标开始获取事件。
5. Agent进行去重、任务生成和状态更新。
6. 对当前可合法保存的内容执行本地任务。
7. 提交处理结果，并在本地安全推进同步游标。

## 6. 非功能需求

### NFR-001：可靠性

- 事件一经成功提交，应具备持久化能力。
- 关键业务写入具有事务性。
- 系统重启后能够恢复未完成的监控及同步任务。
- 支持至少一次事件投递和客户端幂等处理。

### NFR-002：可扩展性

- 新增用户不应按相同比例增加重复监控请求。
- 监控执行器与业务API逻辑解耦。
- 数据获取实现应通过统一Provider接口接入，以便更换或扩展合法数据来源。

### NFR-003：安全与隐私

- 服务端不得持有用户的B站密码、Cookie或其他个人登录密钥。
- 用户订阅关系默认私有。
- 客户端与服务端通信使用HTTPS。
- 设备令牌应支持吊销和轮换。
- 禁止跨用户访问私人订阅、设备或通知数据。
- 监控日志不得泄漏认证信息。
- 保存个人信息时遵守数据最小化原则。

### NFR-004：可观测性

服务端应记录：
- 当前监控目标数
- 最近成功监控时间
- 本次监控结果
- 任务错误及重试次数
- 新增视频和状态事件数
- Agent同步失败情况

### NFR-005：性能

初期面向个人开发和小规模用户群体设计。

并发量、监控周期、日均请求量、状态检测延迟及历史数据容量，需要在确认数据源许可和完成原型压测后制定可执行的指标。

不得为了达到性能指标而突破平台规定的访问频率或权限限制。

### NFR-006：数据保留

公共历史记录仅在合法、必要且符合授权范围的条件下保存。

订阅、日志、设备信息、历史简介和评论等不同数据类型应有独立保留策略，并提供必要的更正及删除机制。

## 7. MVP功能范围

第一版必须完成以下闭环：

| 需求 | 范围 | 优先级 |
|---|---|---|
| 用户账户及UP主/视频订阅 | 服务端 | P0 |
| 监控目标聚合与去重 | 服务端 | P0 |
| 合法或模拟数据源适配 | 服务端 | P0 |
| 视频元数据索引 | 服务端 | P0 |
| 视频状态检测与事件日志 | 服务端 | P0 |
| 视频历史查询页面 | Web | P0 |
| 站内事件通知 | Web | P0 |
| Agent绑定与增量同步 | Agent/服务端 | P0 |
| 本地任务与文件管理 | Agent | P0 |
| 权限、安全、投诉处理 | 全局 | P0 |

MVP应先通过模拟数据源建立完整业务闭环。实际B站数据的自动监控，以及本地内容复制能力，在取得所需授权并验证接口可用性之后才能投入真实运行。

## 8. 系统级验收场景

### AC-001：共享订阅去重

给定两个用户订阅同一个UP主。

当两人完成订阅时，系统应创建两条用户订阅关系，但原则上只有一个UP主级公共监控目标。

### AC-002：用户离线时仍然追踪

给定全部Agent均处于离线状态。

当公共监控发现视频状态变化时，服务端仍应记录事件并更新历史查询结果。

### AC-003：离线事件补偿

给定用户Agent已经离线，并且服务器生成了多条新事件。

当Agent重新连接时，应能够增量获取未处理事件；重复获取不会生成重复任务。

### AC-004：异常状态判断

给定某视频此前可以正常访问。

当一次检查因为网络超时失败时，不应立即确认视频已下架。

### AC-005：视频文件隔离

给定Agent成功保存了一个有权备份的视频。

公共服务器只能收到允许同步的任务元信息，不应收到视频文件或媒体分片。

### AC-006：多用户数据隔离

给定用户A和用户B拥有不同订阅列表和Agent设备。

用户A不得通过API读取或修改用户B的私人订阅、设备、凭据和任务。

### AC-007：历史记录真实性

给定系统从10:00至12:00未检查某个视频，并在12:00首次发现视频不可访问。

系统不得宣称视频恰好在12:00被删除，应显示首次发现异常的时间及最后正常观测时间。

## 9. 外部依赖与风险

| 风险 | 影响 | 处理原则 |
|---|---|---|
| B站自动化访问权限限制 | 核心功能可能无法公开运营 | 优先官方授权接口或合法合作数据源 |
| 授权接口能力不足 | 无法完整发现任意UP主投稿 | 缩小MVP支持范围，不通过绕过限制补齐 |
| 视频状态结果不准确 | 导致错误下架判断 | 多次确认、保留观测依据 |
| 个人信息与评论保护 | 产生隐私和版权风险 | 限制数据范围，支持纠错和删除 |
| Agent离线 | 不能完成及时备份 | 明确产品不保证完整备份 |
| 本地账号凭据泄漏 | 用户账号安全受损 | 凭据本地化、安全存储、最小授权 |
| 任务规模扩大 | 增加数据库和调度压力 | 去重、限流、可观测性和容量规划 |
