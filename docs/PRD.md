## 1. 项目背景

### 1.1 背景与问题

哔哩哔哩（B站）存在大量由UP主持续发布的视频内容。由于UP主主动删除、修改可见范围、版权限制、平台处理等原因，部分历史投稿可能不再能够正常访问。

目前用户主要面临以下问题：

1. **缺少历史记录**：无法方便地查询某个UP主曾经发布过哪些视频。
2. **视频变化不透明**：很难知道某个视频从什么时候开始无法访问。
3. **人工跟踪成本高**：需要反复打开UP主空间检查投稿情况。
4. **私人备份不及时**：用户电脑不在线时，无法执行本地备份，可能错过视频仍然可访问的时间。
5. **订阅与备份缺少联动**：公共信息跟踪和用户私人备份通常由不同工具完成。

### 1.2 产品定位

本项目定位为：

**面向视频平台的持续历史追踪与个人本地发现、备份管理平台，哔哩哔哩为首个适配平台。**

系统由两个相互独立但协同工作的部分构成：

- **公共服务端**：持续跟踪已接纳的目标，保存并提供UP主资料、粉丝数、视频元数据、播放量及历史观测，管理跟踪关系。服务器提供的是自身已经记录的数据，不承诺全站视频或完整历史。
- **本地 Agent 与浏览器界面**：Agent 在回环地址提供网页和同源本地 API，浏览器直接连接 Agent，配置连接、账号、规则和任务；Agent 从服务器同步记录，在本地保存缓存、发现规则和任务，使用用户自己的 Cookie 访问平台，发现UP主当前登录态下可见的视频，按显式规则提交跟踪目标，并按需保存视频和评论区到本地。关闭浏览器页面不影响仍运行的 Agent 执行已提交任务。

平台差异封装在适配器中，通用界面只出现作者、视频和任务，不出现B站合集。公共服务端不接收客户端的平台 Cookie、视频文件、评论正文和本地文件路径，也不提供媒体中转。

浏览器界面与本地 Agent 统一放在 `client/` 下，页面、任务、同步与实施阶段共用 [客户端需求与设计](../client/README.md)，各子目录保留实现职责说明；本文继续维护平台整体产品范围。当前实现范围见 [架构说明](architecture.md)，产品需求中的完整客户端与服务器同步能力尚未全部实现。

当前客户端已实现手动 Cookie 配置与验证、指定 UP 主可见投稿 BV 全量分页、去重、进度、停止/继续、TXT/JSON 导出；Windows Cookie 由当前用户加密保存，其他平台暂仅在进程中保留。普通网页不自动读取 B站 Cookie，扩展仍待后续。当前功能独立运行，不依赖服务器认证与同步，详见 [实现与验证边界](client-discovery.md)。

### 1.3 产品目标

- 为用户提供统一的UP主及视频订阅入口。
- 在合法数据来源允许的情况下，对多个用户订阅的目标进行统一、持续、去重监控。
- 记录视频首次发现、元数据变更及可访问性变化。
- 即使所有本地 Agent 离线，服务器也能够独立维护公共监控记录。
- Agent 重新上线后能够同步离线期间发生的事件。
- 降低个人用户管理备份任务的复杂度。
- 在系统架构层面隔离公共数据与私人视频文件。

### 1.4 非目标

本项目第一版不计划实现：

- 公共视频托管、点播、分享或下载服务。
- 下架视频的重新上传和传播。
- 绕过会员、付费、DRM、登录权限或平台访问限制。
- 视频内容推荐算法。
- 用户之间的P2P视频分享。
- 分布式视频存储网络。
- 全站视频索引或无订阅目标的大规模扫描。

## 2. 用户角色

### 2.1 访客

无需登录，可以查询允许公开展示的UP主历史投稿、视频状态和历史变化记录。

### 2.2 注册用户

可以订阅UP主或单个视频，管理订阅列表、接收通知、设置个人隐私偏好，并绑定本地 Agent。

### 2.3 Agent 用户

已绑定本地设备的工作区管理员或注册用户，可以同步记录、配置本地登录态发现、新投稿规则，以及后续的备份和文件管理选项。

### 2.4 系统管理员

负责监控公共服务健康状态、管理数据源、处理投诉与删除请求、管理异常任务和审查系统运行日志。

## 3. 核心业务规则

**BR-01：订阅与监控分离**

用户订阅关系为私人用户数据，公共监控任务为共享系统资源。

同一UP主被多个用户订阅时，服务端应尽可能复用监控任务，避免不必要的重复请求。

**BR-02：服务器与Agent独立运行**

公共监控服务不依赖用户的Agent在线。

本地Agent离线时，服务器继续记录已知目标，但不替用户执行登录态发现、视频下载或评论区保存。只有本地登录态才能发现的新投稿，要等Agent恢复运行后补发现；服务器此前不知道的目标不能保证有离线期间的记录。

**BR-03：公共服务器不存储视频**

服务器不接收或保存视频媒体文件、分片、视频播放缓存以及本地备份文件。

**BR-04：数据获取需要合法授权**

任何真实监控与备份功能，都必须遵循适用法律、平台协议和数据源授权范围。

无权限访问或使用的数据，不得通过绕过限制的方式获取。

**BR-05：区分观察结果和事实判断**

“视频不可访问”不等于“视频已被删除”，更不等于“视频被平台下架”。

系统只展示具有证据支持的观测状态，不推断无法确定的删除原因。

**BR-06：历史记录不保证完整**

系统只能记录开始监控后，或者从合法历史数据源获得的信息。

首次监控前已经消失的视频，可能无法被发现。

**BR-07：事件持久化与幂等处理**

视频变化事件应具有唯一标识，并支持Agent断线恢复、重复拉取和幂等处理。

## 4. 功能需求

功能优先级定义：

- **P0**：MVP必须实现。
- **P1**：核心闭环完成后的增强功能。
- **P2**：后续扩展功能。

### 4.1 用户及账户模块

**FR-001：工作区访问与账户（P0：设备认证；多用户注册后续扩展）**

首期用户通过设备凭据连接工作区，凭据可撤销、轮换并区分读写权限；账户化后支持创建平台账户、登录和退出。

当前实现没有用户表和登录，只有单管理员工作区。客户端首期可先接入该工作区，以可撤销的设备凭据保护读写；无需为了本地 Cookie 登录提前创建多用户体系，也不能把未鉴权的后台当作设备接口。多用户注册与私人订阅隔离属于后续账户化阶段，不硬编码 `user_id = 1`。

验收标准：
- 未通过设备或账户认证的调用方不能修改跟踪关系。
- 设备只能操作被授权工作区；账户化后只能操作自身的私人订阅和设备。
- 凭据过期或被撤销后，受保护接口拒绝访问。

**FR-002：个人订阅管理（P0）**

用户可以通过UP主UID或视频BV号添加订阅，也可以取消订阅。

单管理员阶段以工作区启用的跟踪目标表达关注，历史记录与关注分开；账户化后再以私人订阅驱动共享目标，迁移规则见 [作者视频设计](video-discovery.md)。下述按用户隔离的验收在账户化阶段执行。

验收标准：
- 同一用户重复订阅同一目标，不产生重复订阅记录。
- 取消某项订阅后，不再收到该订阅产生的新通知。
- 订阅关系默认不公开。
- 添加无效标识时，返回明确错误。

**FR-003：订阅偏好（P1）**

用户可以针对不同UP主或视频分别配置通知及本地备份策略。

### 4.2 公共监控模块

**FR-004：监控目标聚合（P0）**

服务端汇总所有用户订阅的UP主及视频，维护统一的监控目标集合。

验收标准：
- 多个用户订阅同一UP主，默认只生成一个对应的UP主监控目标。
- 用户之间的订阅数据保持隔离。
- 最后一个订阅者取消后，目标可以停止主动监控，具体清理策略由后续设计确定。

**FR-005：UP主投稿发现（P0）**

服务器提供自身可获取的视频发现能力；本地Agent可使用用户 Cookie 枚举当前登录态下可见的投稿，并向服务器提交选定的视频标识。服务器重新查询、校验归属及公共可采集性后，建立跟踪并写入自己的观测，不直接信任客户端元数据。

关注UP主资料、选择历史视频、自动跟踪新投稿是独立操作。历史候选默认全部不选，提供跨页“一键添加全部”；自动跟踪新投稿必须显式开启本地发现规则。规则首次扫描建立基线，历史视频不自动添加。服务器资料采集本身不隐含自动跟踪该UP主全部视频。

“全部”指本次数据源和当前登录态可枚举的可见范围。分页中断或权限不足时显示部分结果，不承诺包括隐藏或已删除投稿。仅本地可访问的视频不能显示为服务器已成功跟踪。

系统至少记录：
- UP主UID
- 视频BV号
- 视频标题
- 原始投稿时间
- 系统首次发现时间
- 数据来源和观测时间

系统还可根据数据来源许可记录简介、分P结构及统计数据等非媒体信息。

**FR-006：视频可访问性监控（P0）**

定期检查已记录视频的可访问状态。

建议支持以下状态：

| 状态 | 含义 |
|---|---|
| UNKNOWN | 尚无可靠判断 |
| AVAILABLE | 已确认当前可访问 |
| SUSPECTED_UNAVAILABLE | 疑似不可访问，尚待确认 |
| CONFIRMED_UNAVAILABLE | 经多次有效检查，确认当前无法正常访问 |
| ACCESS_RESTRICTED | 受到权限或地区等访问条件限制 |
| CHECK_FAILED | 本次检查失败，结果不可信 |

如果历史异常的视频恢复正常访问，应当记录恢复事件。

验收标准：
- 网络超时或接口故障不会直接产生“已删除”结论。
- 可配置重试、确认次数及检查间隔。
- 系统记录最后一次成功检查和首次发现异常的时间。
- 保留能说明状态判断依据的非敏感证据。

**FR-007：历史元数据版本管理（P1）**

当视频标题、简介等允许记录的字段发生变化时，生成历史版本或字段变更记录。

只在实际变化时保存必要的增量或快照，避免重复保存大量相同内容。

**FR-008：公共历史查询（P0）**

访客和注册用户可按照UP主UID、视频BV号查询已有的公开历史索引。

展示内容包括：
- 视频基本信息
- 当前观测状态
- 首次发现时间
- 最后确认正常时间
- 首次发现异常时间
- 主要历史状态事件

搜索与展示需要明确区分真实观测数据和未知数据。

### 4.3 事件与通知模块

**FR-009：视频事件日志（P0）**

当监控目标出现有意义的变化时，服务器产生持久化事件。

事件类型包括：
- VIDEO_DISCOVERED：发现新投稿
- VIDEO_METADATA_CHANGED：视频元数据变更
- VIDEO_UNAVAILABLE：确认视频不可访问
- VIDEO_RECOVERED：视频恢复访问
- VIDEO_ACCESS_RESTRICTED：访问权限变化

每个事件至少包含事件ID、目标标识、事件类型、观测时间及必要的变更信息。

**FR-010：订阅事件通知（P0）**

服务器按订阅关系将相关事件分发给注册用户。

MVP阶段支持站内通知；邮件、Web Push等作为后续增强。

重复观测不得持续产生相同的通知。

**FR-011：Agent增量同步（P0）**

Agent使用服务端同步游标获取未处理事件。

验收标准：
- 断线后能从已确认游标继续拉取。
- 事件重复下发不会造成重复任务。
- 只有完成本地事务性持久化后才能推进同步游标。
- 用户无权访问其他用户的私人事件。
- 游标过期或历史事件已清理时，支持重新获取状态快照并恢复同步。
- 事件、派生任务意图与新游标在同一本地事务中落盘；无需等待视频或评论下载完成才推进游标。
- 记录同步游标与平台发现续页独立保存；服务器实例或数据代次改变时重新对账，不能复用旧游标。

### 4.4 本地Agent模块

**FR-012：Agent设备绑定（P0）**

用户可以将自己的Agent设备绑定到服务器工作区；账户化后绑定到当前用户。

设备应拥有独立的身份凭据，用户可查看、撤销和重新绑定设备。

**FR-013：本地备份任务管理（P1，受授权条件约束）**

Agent可以根据用户选择的策略，对具备合法复制权限且当前可获取的内容创建本地备份任务。

备份规则包括：
- 仅备份新增视频。
- 备份允许访问的历史视频及新增视频。
- 仅接收通知，手动选择备份。
- 完全关闭备份。

默认关闭自动备份。服务器跟踪、本地新视频发现、视频下载和评论区保存分别配置，下载任务直接连接平台，不经服务器转发。

验收标准：
- Agent离线时不会假装备份成功。
- 用户可暂停、恢复和取消本地任务。
- 对已备份的视频进行去重。
- 备份失败时记录可理解的错误。
- 视频不可访问或权限不足时，不绕过访问限制。

**FR-014：本地文件管理（P1）**

备份文件保存到用户指定目录，相关状态记录存储在本地数据库中。

允许记录文件路径、备份时间、文件大小、任务状态及可选校验信息。

**FR-015：本地敏感凭据管理（P0）**

若使用用户B站账号，Cookie 通过本地界面交给本地Agent，只能保存在用户设备上，不得同步至公共服务器。B站登录状态与服务器连接凭据分别管理；失效时暂停相关平台任务并提示更新，不能反复无效重试。

优先使用官方允许的认证方式和操作系统安全凭据存储。

服务端不得通过Agent执行任意系统命令。

**FR-016：离线事件补偿（P0）**

Agent恢复在线后：
1. 增量同步服务器记录；事件、状态、任务意图和游标在本地事务中一起提交。
2. 恢复本地发现规则，分页补扫离线期间可能新增的投稿，并去重。
3. 重放待提交的视频标识，按服务器确认结果更新跟踪状态。
4. 按单独开启的备份规则，检查内容当前是否可获取并执行本地任务。

服务器离线时，本地仍可使用有效 Cookie 发现和下载，跟踪申请保存在本地等待重连。系统不保证补齐未曾观测的统计、离线期间已经消失的投稿或媒体文件。

**FR-020：本地登录态发现与新投稿规则（P0）**

支持输入平台与作者标识，使用本地 Cookie 分页获取当前可见的视频。任务保留进度、去重集合、最后成功时间和不完整原因；平台细节封装在本地适配器中。

用户可以单独开启“跟踪UP主新视频”。首次完整扫描建立基线，随后周期发现新增视频，按规则提交服务器跟踪；自动下载仍默认关闭。离线补扫不能只检查第一页或仅比较投稿时间。取消发现规则不自动停止服务器已有视频跟踪，也不删除本地文件。

**FR-021：客户端记录浏览与任务界面（P0）**

界面运行在浏览器中，由本地 Agent 同源提供网页和 HTTP API。启动 Agent 后即可打开本地页面，日常使用无需前端开发服务。配置由 Agent 校验并持久化，敏感凭据不经配置读取接口回传网页；关闭或刷新页面不取消已提交任务，Agent 停止时页面提示断连，重新启动后恢复持久化状态。浏览器统一经 Agent 访问服务器与平台。

界面提供UP主及视频列表、详情、粉丝数和播放量趋势、历史版本、发现规则、任务与连接设置。服务器观测、本地发现和本地文件状态分别标识来源及时间；离线时可浏览本地缓存，并显示缓存更新时间。

支持直接输入平台视频标识或链接并提交单视频跟踪，无需先枚举作者；本地适配器负责解析及登录态补充查询，服务器仍独立校验。

分页列表保留选择；历史候选默认不勾选，“一键添加全部”涵盖未加载页并显示进度。服务器确认前显示待提交或失败，不能仅按本地已发现推断已在服务器跟踪。文件管理在P1、评论区保存入口在P2实现。

**FR-019：本地评论区保存（P2）**

用户显式选择视频后，可由本地Agent独立分页保存当前可见的评论与回复，记录视频标识、评论标识、父子关系、观测时间及完整性。支持本地查看与导出，不依赖先下载视频。

评论正文和导出文件留在本地，不上传服务器。限流、权限变化或中断时保留部分结果，不承诺恢复已删除评论或获取不可见的全部评论；公共评论历史归档不纳入本方案。

### 4.5 管理与合规模块

**FR-017：监控任务管理（P0）**

管理员能够查看监控任务数量、执行状态、最近成功时间、错误原因和数据源健康情况。

**FR-018：投诉、纠错及删除处理（P0，上线前必备）**

提供公共信息纠错、隐私投诉、侵权投诉和数据删除申请渠道。

依据适用规则处理请求，并记录处理结果。

## 5. 核心业务流程

### 5.1 用户订阅UP主

1. 用户连接已认证的工作区，账户化后登录自己的账户。
2. 输入目标UP主UID。
3. 系统验证输入及是否具有合法数据访问方式。
4. 系统创建用户订阅关系。
5. 若公共监控任务已存在，直接复用。
6. 若目标尚未监控且满足数据来源条件，创建监控任务。
7. 系统展示当前已知投稿与历史事件。

### 5.2 本地发现与服务器跟踪协作

1. 用户配置本地 Cookie，输入UP主并分页扫描当前可见视频。
2. 历史候选默认不选；用户选择部分视频或一键添加全部。
3. 本地持久化跟踪申请，仅向服务器提交平台、作者和视频标识。
4. 服务器公开查询并校验，接纳后加入共享跟踪；仅本地可访问的候选保留本地状态并说明原因。
5. 若用户另外开启新投稿规则，先完成基线，再周期发现新视频并按规则提交。
6. 服务器持续采集已接纳目标，客户端同步记录与后续变化；下载、评论区保存按独立本地策略执行。

服务器自身的公开发现可作为补充入口，不依赖本地 Cookie，也不替代本地登录态发现。

### 5.3 服务器发现视频异常

1. 某个视频本次检查无法访问。
2. 系统保存观测结果，并判断是否需要重新确认。
3. 在缺少充分证据时，标记为疑似异常。
4. 多次有效检查满足规则后，记录确认不可访问事件。
5. 公共页面展示最后确认正常时间和首次异常时间。
6. 向相关订阅用户发送状态变化通知。

### 5.4 Agent离线与恢复

1. Agent离线，公共监控服务照常运行。
2. 服务端持续生成并保存视频变化事件。
3. 用户重新启动Agent。
4. Agent从自身同步游标开始获取事件。
5. Agent在本地事务中完成去重、任务意图、状态与游标的持久化。
6. 独立恢复作者分页补发现及待提交申请，服务器确认后更新跟踪状态。
7. 若开启本地备份，则恢复可执行的下载任务；下载进度不阻塞记录同步游标。

## 6. 非功能需求

### NFR-001：可靠性

- 事件一经成功提交，应具备持久化能力。
- 关键业务写入具有事务性。
- 系统重启后能够恢复未完成的监控及同步任务。
- 支持至少一次事件投递和客户端幂等处理。

### NFR-002：可扩展性

- 新增用户不应按相同比例增加重复监控请求。
- 监控执行器与业务API逻辑解耦。
- 数据获取实现应通过统一Provider接口接入，以便更换或扩展合法数据来源。

### NFR-003：安全与隐私

- 服务端不得持有用户的B站密码、Cookie或其他个人登录密钥。
- 用户订阅关系默认私有。
- Agent 与远端服务端通信使用 HTTPS；浏览器与本地 Agent 使用回环 HTTP，限制 Host/Origin 并验证本地会话，写操作提供 CSRF 防护。
- 设备令牌应支持吊销和轮换。
- 禁止跨用户访问私人订阅、设备或通知数据。
- 监控日志不得泄漏认证信息。
- 保存个人信息时遵守数据最小化原则。

### NFR-004：可观测性

服务端应记录：
- 当前监控目标数
- 最近成功监控时间
- 本次监控结果
- 任务错误及重试次数
- 新增视频和状态事件数
- Agent同步失败情况

### NFR-005：性能

初期面向个人开发和小规模用户群体设计。

并发量、监控周期、日均请求量、状态检测延迟及历史数据容量，需要在确认数据源许可和完成原型压测后制定可执行的指标。

不得为了达到性能指标而突破平台规定的访问频率或权限限制。

### NFR-006：数据保留

公共历史记录仅在合法、必要且符合授权范围的条件下保存。

订阅、日志、设备信息、历史简介和评论等不同数据类型应有独立保留策略，并提供必要的更正及删除机制。

第一版必须完成以下闭环：

| 需求 | 范围 | 优先级 |
|---|---|---|

| 监控目标聚合与去重 | 服务端 | P0 |
| 合法或模拟数据源适配 | 服务端 | P0 |
| 视频元数据索引 | 服务端 | P0 |
| 视频状态检测与事件日志 | 服务端 | P0 |
| 视频历史查询页面 | Web | P0 |
| 站内事件通知 | Web | P0 |

## 8. 系统级验收场景

### AC-001：共享订阅去重

给定两个用户订阅同一个UP主。

当两人完成订阅时，系统应创建两条用户订阅关系，但原则上只有一个UP主级公共监控目标。

本场景在账户化阶段验收；单管理员首期验证多个设备重复提交仍复用同一跟踪目标。

### AC-002：用户离线时仍然追踪

给定全部Agent均处于离线状态。

当公共监控发现视频状态变化时，服务端仍应记录事件并更新历史查询结果。

### AC-003：离线事件补偿

给定用户Agent已经离线，并且服务器生成了多条新事件。

当Agent重新连接时，应能够增量获取未处理事件；重复获取不会生成重复任务。

### AC-004：异常状态判断

给定某视频此前可以正常访问。

当一次检查因为网络超时失败时，不应立即确认视频已下架。

### AC-005：视频文件隔离

给定Agent成功保存了一个有权备份的视频。

公共服务器只能收到选定的公共跟踪标识及必要的请求信息，不应收到平台 Cookie、视频文件、媒体分片、评论正文或本地文件路径。

### AC-006：多用户数据隔离

给定用户A和用户B拥有不同订阅列表和Agent设备。

用户A不得通过API读取或修改用户B的私人订阅、设备、凭据和任务。

本场景在账户化阶段验收；单管理员首期验证设备权限、工作区边界及撤销生效。

### AC-007：历史记录真实性

给定系统从10:00至12:00未检查某个视频，并在12:00首次发现视频不可访问。

系统不得宣称视频恰好在12:00被删除，应显示首次发现异常的时间及最后正常观测时间。

### AC-008：历史选择与新投稿规则分离

首次扫描包含多页历史视频时，全部默认未选；一键添加全部覆盖未加载页。单独开启新投稿规则只以完整基线后的新增视频触发自动跟踪，历史视频和自动下载不被隐式开启。

### AC-009：离线补发现与双向断连

本地离线期间新增视频超过一页时，恢复后分页补扫并去重，不能只读取最新一页。服务器继续采集此前已知目标；服务器断连期间的本地发现保存在本地，重连后幂等提交。已消失或缺乏观测的数据明确标为缺失。

### AC-010：凭据与本地任务隔离

服务器认证过期不影响本地有效 Cookie 的独立任务；B站 Cookie 失效不影响读取服务器历史。启用下载或评论保存后，任务重启可恢复且不重复完成，文件及评论始终留在本地。

## 9. 外部依赖与风险

| 风险 | 影响 | 处理原则 |
|---|---|---|
| B站自动化访问权限限制 | 核心功能可能无法公开运营 | 优先官方授权接口或合法合作数据源 |
| 授权接口能力不足 | 无法完整发现任意UP主投稿 | 缩小MVP支持范围，不通过绕过限制补齐 |
| 视频状态结果不准确 | 导致错误下架判断 | 多次确认、保留观测依据 |
| 个人信息与评论保护 | 产生隐私和版权风险 | 限制数据范围，支持纠错和删除 |
| Agent离线 | 不能完成及时备份 | 明确产品不保证完整备份 |
| 本地账号凭据泄漏 | 用户账号安全受损 | 凭据本地化、安全存储、最小授权 |
| 任务规模扩大 | 增加数据库和调度压力 | 去重、限流、可观测性和容量规划 |

## 10. 后续版本规划

**V0.1：需求验证与最小闭环**

在现有服务端查询、持久化与观察台基础上，补齐设备认证、记录读取、Agent发现和同步闭环；使用Mock Provider验证分页、状态事件、断连与任务恢复。

**V0.2：合法真实数据接入**

在现有公开查询之外，验证本地 Cookie 可用的发现能力，完善真实平台接入；按 [客户端阶段](../client/README.md#实施阶段与验收) 扩展本地视频下载，后续再接入本地评论保存。

**V0.3：用户体验完善**

完善历史时间线、通知、可配置监控策略和客户端任务管理。

**V1.0：可公开使用版本**

完成必要的合规、安全、稳定性、部署、监控及用户数据管理要求后正式发布。
