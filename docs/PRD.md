## 1. 项目背景

### 1.1 背景与问题

哔哩哔哩（B站）存在大量由UP主持续发布的视频内容。由于UP主主动删除、修改可见范围、版权限制、平台处理等原因，部分历史投稿可能不再能够正常访问。

目前用户主要面临以下问题：

1. **缺少历史记录**：无法方便地查询某个UP主曾经发布过哪些视频。
2. **视频变化不透明**：很难知道某个视频从什么时候开始无法访问。
3. **人工跟踪成本高**：需要反复打开UP主空间检查投稿情况。
4. **私人备份不及时**：用户电脑不在线时，无法执行本地备份，可能错过视频仍然可访问的时间。
5. **订阅与备份缺少联动**：公共信息跟踪和用户私人备份通常由不同工具完成。

### 1.2 产品定位

本项目定位为：

**面向视频平台的持续历史追踪与个人本地发现、备份管理平台，哔哩哔哩为首个适配平台。**

系统由两个相互独立但协同工作的部分构成：

- **公共服务端**：持续跟踪已接纳的目标，保存并提供UP主资料、粉丝数、视频元数据、播放量及历史观测，管理公共目标，不保存谁关注谁。服务器提供的是自身已经记录的数据，不承诺全站视频或完整历史。
- **本地 Agent 与浏览器界面**：Agent 在回环地址提供网页和同源 API，本地管理私人关注 UP/视频库，按标识查询公共资料、版本和指标历史，必要时提交公共采集申请；使用留在本机的 Cookie 按需搜索发现和下载。Agent 不运行本地长期跟踪规则，保存私人关注、配置、可清理缓存、待确认申请和下载/扫描进度；关闭网页不停止已提交任务。

平台差异封装在适配器中，通用界面只出现作者、视频和任务，不出现B站合集。公共服务端不接收客户端的平台 Cookie、视频文件、评论正文和本地文件路径，也不提供媒体中转。

浏览器界面与本地 Agent 统一放在 `client/` 下，页面、任务、同步与实施阶段共用 [客户端需求与设计](../client/README.md)，各子目录保留实现职责说明；本文继续维护平台整体产品范围。当前实现范围见 [架构说明](architecture.md)，产品需求中的完整客户端与服务器同步能力尚未全部实现。

当前客户端已实现 Cookie 投稿扫描与导出，以及本地关注 UP/视频库、服务器配置、目标提交和资料/指标/版本读取；关注保存在本地，取消不全局停采。更新后的8182共用原查询与调度，当前按可信服务部署，不代表公共准入全部完成。实现与验证见 [关注接入](client-library.md) 和 [发现实现](client-discovery.md)。

后续目标是下载、完整数据管理、云盘、公共准入及搜索/批量增强；评论和弹幕继续留待后续。整体目标见 [协作设计](client-server-architecture.md)，不得将需求清单全部视为已交付代码。

私人资料、关注和偏好由用户自行管理，规划通过 Agent 提供数据概览、导入导出、备份恢复与清理，未来直接自动备份到用户配置的个人云盘；公共跟踪服务器不托管私人档案或云盘凭据，见 [数据管理设计](client-data-management.md)。

### 1.3 产品目标

- 为用户提供统一的UP主及视频订阅入口。
- 在合法数据来源允许的情况下，对多个客户端申请的公共目标进行统一、持续、去重监控。
- 记录视频首次发现、元数据变更及可访问性变化。
- 即使所有本地 Agent 离线，服务器也能够独立维护公共监控记录。
- Agent 重新上线后能够同步离线期间发生的事件。
- 降低个人用户管理备份任务的复杂度。
- 在系统架构层面隔离公共数据与私人视频文件。

### 1.4 非目标

本项目第一版不计划实现：

- 公共视频托管、点播、分享或下载服务。
- 下架视频的重新上传和传播。
- 绕过会员、付费、DRM、登录权限或平台访问限制。
- 视频内容推荐算法。
- 用户之间的P2P视频分享。
- 分布式视频存储网络。
- 全站视频索引或无订阅目标的大规模扫描。

## 2. 用户角色

### 2.1 公共数据访问者

按服务策略查询允许公开的 UP/视频资料、版本和指标历史，不需要创建服务器个人账户。

### 2.2 本地使用者

在自己的 Agent 保存关注、偏好、Cookie 和文件，查询公共历史、按需发现、申请公共采集并下载，不向服务器同步个人关注清单。

### 2.3 本地档案使用者

优先一人一 Agent 和独立目录。档案保存本地标识、名称、关注与偏好，用户可自行备份、迁移，未来选择个人云盘同步；不代表公共服务器验证过的身份。若多人共用一个实例，需额外实现本地登录与存储隔离，档案选择不等于安全隔离。

### 2.4 系统管理员

控制公共目标、预算、准入、暂停、清理、纠错和服务凭据。普通客户端没有全局停采、修改间隔或删除公共历史的权限。

## 3. 核心业务规则

**BR-01：个人关注与公共监控分离**

个人关注关系只保存在各自 Agent，服务器维护共享目标与历史，不保存谁关注谁。相同目标申请去重后复用公共采集。

本地取消不停止公共跟踪；服务器不知道全部私人关注，不能推断最后一个人已取消。降频、暂停和保留由管理员策略控制。

**BR-02：服务器与Agent独立运行**

公共监控服务不依赖用户的Agent在线。

本地 Agent 离线时，服务器继续记录已知目标，不替用户执行本地登录态发现或文件下载。Agent 不维护本地周期跟踪任务；仅本地登录态可发现的候选由用户恢复后按需扫描，服务器此前不知道的目标不保证有离线期间的记录。

**BR-03：公共服务器不存储视频**

服务器不接收或保存视频媒体文件、分片、视频播放缓存以及本地备份文件。

**BR-04：数据获取需要合法授权**

任何真实监控与备份功能，都必须遵循适用法律、平台协议和数据源授权范围。

无权限访问或使用的数据，不得通过绕过限制的方式获取。

**BR-05：区分观察结果和事实判断**

“视频不可访问”不等于“视频已被删除”，更不等于“视频被平台下架”。

系统只展示具有证据支持的观测状态，不推断无法确定的删除原因。

**BR-06：历史记录不保证完整**

系统只能记录开始监控后，或者从合法历史数据源获得的信息。

首次监控前已经消失的视频，可能无法被发现。

**BR-07：事件持久化与幂等处理**

视频变化事件应具有唯一标识，并支持Agent断线恢复、重复拉取和幂等处理。

## 4. 功能需求

功能优先级定义：

- **P0**：MVP必须实现。
- **P1**：核心闭环完成后的增强功能。
- **P2**：后续扩展功能。

### 4.1 本地关注与服务访问

**FR-001：服务准入（P0，不含用户注册登录）**

多人共用公共数据池，服务器不建设个人账户、私人工作区或订阅表。公共查询和新增采集分别控制，使用 HTTPS、有界队列、限流、批量与总目标预算；部署可发放可撤销的安装访问凭据，不绑定个人关注。

当前仍只有本地管理入口，公共 API 和准入待实现。普通客户端不能视为管理员，不在客户端内置共享管理员密钥。

验收标准：
- 新增目标有预算和去重，重复申请不反复即时采集。
- 普通客户端不能全局停采、删除历史或修改间隔。
- 若启用访问凭据，撤销后拒绝受限操作；不要求保存用户账号或私人关注。

**FR-002：本地个人关注（P0）**

Agent 通过 UID/BV 添加或取消个人关注，保存本地列表，按标识查询公共资料与跟踪状态；关注、公共记录存在和正在跟踪分别显示。

添加关注可申请公共采集，申请失败不删除本地关注。本地取消只影响自己，可取消未发出的申请，不撤回已接纳公共任务，不删除历史或文件。

验收标准：
- 同一本地档案重复添加不产生重复项，两个 Agent 私人列表互不影响。
- 本地列表不是服务器全局目标，不上传为个人云端订阅。
- 无效标识明确报错，未确认采集前不显示服务器跟踪成功。
- 本地数据丢失不承诺由公共跟踪服务器恢复，由用户通过档案导入/备份恢复管理。
- 用户可通过 Agent 的档案管理自行备份与恢复，未来可从自选存储恢复，不依赖公共服务器账户。

**FR-003：本地偏好（P1）**

通知、目录、下载和显示偏好留本地。完整本地账户仅在多人共用一个 Agent 时评估，现有单份配置未提供此类隔离。

### 4.2 公共监控模块

**FR-004：公共目标接纳与去重（P0）**

服务器接收采集申请，不接收私人订阅关系；按 `(platform, kind, id)` 去重，并发申请在查询和最终写入两层合并。

- 已跟踪：返回已有状态，不因每次申请立即刷新或改变间隔。
- 有记录未跟踪：按管理员策略恢复或拒绝，不绕过暂停/拒绝名单。
- 未有记录：调用可信公开查询，验证成功后保存数据并加入跟踪，失败不伪造有效记录。
- 仍在处理：返回待处理，入队不等于验证完成或正在跟踪。
- 无效、不可公开采集或超额：给出失败或等待原因。

公共查询不隐式增加跟踪；普通客户端只能申请采集，不能停采或删除公共目标。公共清理策略与本地取消无关。

**FR-005：UP主投稿发现（P0）**

服务器提供自身可获取的视频发现能力；本地Agent可使用用户 Cookie 枚举当前登录态下可见的投稿，并向服务器提交选定的视频标识。服务器重新查询、校验归属及公共可采集性后，建立跟踪并写入自己的观测，不直接信任客户端元数据。

关注 UP 主资料、选择其视频和本地下载是独立操作。历史候选默认不选，提供跨页“一键添加全部”；Agent 不执行周期新投稿跟踪。未来若增加自动规则，由服务器在可访问范围内执行；关注 UP 不隐含自动关注其全部视频。

“全部”指本次数据源和当前登录态可枚举的可见范围。分页中断或权限不足时显示部分结果，不承诺包括隐藏或已删除投稿。仅本地可访问的视频不能显示为服务器已成功跟踪。

系统至少记录：
- UP主UID
- 视频BV号
- 视频标题
- 原始投稿时间
- 系统首次发现时间
- 数据来源和观测时间

系统还可根据数据来源许可记录简介、分P结构及统计数据等非媒体信息。

**FR-006：视频可访问性监控（P0）**

定期检查已记录视频的可访问状态。

建议支持以下状态：

| 状态 | 含义 |
|---|---|
| UNKNOWN | 尚无可靠判断 |
| AVAILABLE | 已确认当前可访问 |
| SUSPECTED_UNAVAILABLE | 疑似不可访问，尚待确认 |
| CONFIRMED_UNAVAILABLE | 经多次有效检查，确认当前无法正常访问 |
| ACCESS_RESTRICTED | 受到权限或地区等访问条件限制 |
| CHECK_FAILED | 本次检查失败，结果不可信 |

如果历史异常的视频恢复正常访问，应当记录恢复事件。

验收标准：
- 网络超时或接口故障不会直接产生“已删除”结论。
- 可配置重试、确认次数及检查间隔。
- 系统记录最后一次成功检查和首次发现异常的时间。
- 保留能说明状态判断依据的非敏感证据。

**FR-007：历史元数据版本管理（P1）**

当视频标题、简介等允许记录的字段发生变化时，生成历史版本或字段变更记录。

只在实际变化时保存必要的增量或快照，避免重复保存大量相同内容。

**FR-008：公共历史查询（P0）**

访客和本地客户端可按照UP主UID、视频BV号查询已有的公开历史索引，无需用户注册。

展示内容包括：
- 视频基本信息
- 当前观测状态
- 首次发现时间
- 最后确认正常时间
- 首次发现异常时间
- 主要历史状态事件

搜索与展示需要明确区分真实观测数据和未知数据。

### 4.3 事件与通知模块

**FR-009：视频事件日志（P0）**

当监控目标出现有意义的变化时，服务器产生持久化事件。

事件类型包括：
- VIDEO_DISCOVERED：发现新投稿
- VIDEO_METADATA_CHANGED：视频元数据变更
- VIDEO_UNAVAILABLE：确认视频不可访问
- VIDEO_RECOVERED：视频恢复访问
- VIDEO_ACCESS_RESTRICTED：访问权限变化

每个事件至少包含事件ID、目标标识、事件类型、观测时间及必要的变更信息。

**FR-010：本地关注事件通知（后续增强）**

服务器可提供公共变化事件，Agent 按本地关注过滤通知，不上传私人订阅清单；重复事件不重复通知。

邮件、Web Push 和跨设备个人通知若需云端保存收件人与订阅，另行评估身份和隐私，不作为当前数据池前置条件。

**FR-011：Agent增量同步（后续增强）**

近期先按需分页读取服务器记录和对账关注，不将完整事件复制作为客户端库和手动下载的前置条件。后续可使用服务端同步游标获取未处理事件。

验收标准：
- 断线后能从已确认游标继续拉取。
- 事件重复下发不会造成重复任务。
- 只有完成本地事务性持久化后才能推进同步游标。
- 事件只含允许公开的信息，由 Agent 按本地关注过滤；不上传私人订阅。
- 游标过期或历史事件已清理时，支持重新获取状态快照并恢复同步。
- 事件、派生任务意图与新游标在同一本地事务中落盘；无需等待视频或评论下载完成才推进游标。
- 记录同步游标与平台发现续页独立保存；服务器实例或数据代次改变时重新对账，不能复用旧游标。

### 4.4 本地Agent模块

**FR-012：客户端访问凭据（按部署启用）**

服务可为安装实例发放可撤销、可轮换且受配额限制的访问凭据，用于查询或采集申请准入，不绑定私人关注账户。管理员权限独立，不发给普通客户端。

必要访问记录用于运营和滥用处理，不等于私人订阅表。查询与申请仍发送目标标识，日志可能有来源和时间，不承诺匿名或双方完全无关联。

**FR-013：本地备份任务管理（P1，受授权条件约束）**

Agent可以根据用户选择的策略，对具备合法复制权限且当前可获取的内容创建本地备份任务。

近期实现用户在视频库或发现结果中显式选择视频，配置本地目录、可获取清晰度及分 P 范围，创建下载任务。媒体直接从平台到本地，不经服务器转发；默认不自动下载全部关注。关注、下载、后续评论和弹幕文件分别管理，Agent 不通过周期平台扫描维护自己的长期跟踪。

任务保存进度、失败原因及文件信息，支持暂停、继续、取消和重启恢复；上游支持时才续传，需要音视频合并时明确工具依赖。元数据历史版本不代表存在对应历史媒体文件，只能下载当前仍可访问的媒体。

验收标准：
- Agent离线时不会假装备份成功。
- 用户可暂停、恢复和取消本地任务。
- 对已备份的视频进行去重。
- 备份失败时记录可理解的错误。
- 视频不可访问或权限不足时，不绕过访问限制。

**FR-014：本地文件管理（P1）**

备份文件保存到用户指定目录，相关状态记录存储在本地数据库中。

允许记录文件路径、备份时间、文件大小、任务状态及可选校验信息。

**FR-015：本地敏感凭据管理（P0）**

若使用用户B站账号，Cookie 通过本地界面交给本地Agent，使用系统凭据保护，不得同步至公共跟踪服务器。默认不随档案导出；未来用户明确选择时，可使用自己持有的密钥加密后备份至个人存储。B站登录状态、服务器连接凭据、云盘授权和备份密钥分别管理；失效时暂停相关能力并提示更新，不能反复无效重试。

优先使用官方允许的认证方式和操作系统安全凭据存储。

服务端不得通过Agent执行任意系统命令。

**FR-016：离线事件补偿（P0）**

Agent恢复在线后：
1. 按服务策略恢复查询与申请权限，读取公共记录和历史；后续如接事件同步，再事务保存记录、任务意图及游标。
2. 恢复用户已发起的扫描检查点，不自动创建周期平台跟踪。
3. 对账公共采集申请，分别显示本地关注和服务器状态。
4. 恢复用户已创建的本地下载任务，重新解析当前可获取的媒体。

服务器离线时，本地仍可使用有效 Cookie 发现和下载，跟踪申请保存在本地等待重连。系统不保证补齐未曾观测的统计、离线期间已经消失的投稿或媒体文件。

**FR-020：本地按需搜索与登录态发现（P0）**

支持输入平台与作者标识，使用本地 Cookie 分页获取当前可见的视频。任务保留进度、去重集合、最后成功时间和不完整原因；平台细节封装在本地适配器中。

本地支持 UID/BV/空间或视频链接查找，并按平台能力扩展关键词搜索。服务器记录搜索与平台发现注明来源。Agent 只处理显式发起的任务，不提供本地周期跟踪规则；扫描不自动关注或下载，停止扫描不改变本地关注或公共跟踪。

**FR-021：客户端记录浏览与任务界面（P0）**

界面运行在浏览器中，由本地 Agent 同源提供网页和 HTTP API。启动 Agent 后即可打开本地页面，日常使用无需前端开发服务。配置由 Agent 校验并持久化，敏感凭据不经配置读取接口回传网页；关闭或刷新页面不取消已提交任务，Agent 停止时页面提示断连，重新启动后恢复持久化状态。浏览器统一经 Agent 访问服务器与平台。

界面参考 8182，分为关注 UP 库、关注视频库、搜索发现、下载任务和设置。两个库使用本地私人关注，按标识合并服务器公共数据，支持资料/内容版本、粉丝及播放趋势、选定区间的增减；样本不足显示未知，保留负增长。UP 详情可按需获取全部可见视频并选择关注，视频详情可创建本地下载。缓存和平台候选分别标明来源与时间。

支持直接输入平台视频标识或链接并提交单视频跟踪，无需先枚举作者；本地适配器负责解析及登录态补充查询，服务器仍独立校验。

分页列表保留选择；历史候选默认不选，“一键添加全部”涵盖未加载页并显示进度。本地关注立即保存，采集未确认前单独显示待处理或失败；取消只删除本地列表，不全局停采或删除历史及文件。视频下载与文件管理为近期目标，评论和弹幕入口在后续实现。

**FR-019：本地评论区保存（P2）**

用户显式选择视频后，可由本地Agent独立分页保存当前可见的评论与回复，记录视频标识、评论标识、父子关系、观测时间及完整性。支持本地查看与导出，不依赖先下载视频。

评论正文和导出文件留在本地，不上传服务器。限流、权限变化或中断时保留部分结果，不承诺恢复已删除评论或获取不可见的全部评论；公共评论历史归档不纳入本方案。

**FR-022：本地弹幕文件（P2）**

后续提供独立弹幕下载任务，关联视频及分 P，记录范围、进度和完整性，只保存到本地。视频、评论、弹幕分别启用，某一项完成不代表其他项完成；格式与平台适配后续确定。

**FR-023：用户自主管理本地档案（P1）**

提供“数据管理”页面，查看档案、数据目录和分类占用，管理用户资料、关注与偏好，提供导入导出、一致性备份、预览恢复、合并及分类清理。导入或切换不自动发起采集申请、下载或文件删除；关注、缓存、任务记录与媒体分别控制。

备份包含格式版本、档案标识、范围和校验；恢复前创建回滚点，损坏、不兼容或解密失败不得破坏原档案，任务/路径恢复后重新核验。当前扫描导出不等于完整档案备份，此能力待实施。

**FR-024：用户自选存储的自动备份与同步（P2）**

Agent 直接连接用户配置的云盘或存储服务器，提供连接测试、自动计划、立即备份、历史版本、暂停、重试、保留与恢复。公共跟踪服务器不接收私人档案、云盘凭据或恢复密钥，不以项目用户账户为前提。

首个阶段上传版本化加密备份并按需恢复；默认备份关注/可迁移设置，任务索引可选，媒体与敏感凭据单独选择。云盘授权和解密密钥保留本机，用户在新设备自行连接云盘与提供密钥；本机 DPAPI 文件不能作为通用异机登录恢复包。

失败上传不覆盖最后成功版本，多设备备份独立保存。真正的双向同步需另外实现版本、删除标记与冲突处理，不直接同步活动数据库，不静默按修改时间覆盖。完整边界与验收见 [数据管理设计](client-data-management.md)。

### 4.5 管理与合规模块

**FR-017：监控任务管理（P0）**

管理员能够查看监控任务数量、执行状态、最近成功时间、错误原因和数据源健康情况。

**FR-018：投诉、纠错及删除处理（P0，上线前必备）**

提供公共信息纠错、隐私投诉、侵权投诉和数据删除申请渠道。

依据适用规则处理请求，并记录处理结果。

## 5. 核心业务流程

### 5.1 本地关注与公共跟踪

1. 用户输入 UID/BV，Agent 保存本地关注。
2. 查询公共记录与跟踪状态，已跟踪则复用。
3. 未跟踪时按服务准入提交目标标识。
4. 服务器区分已有数据、未知目标和暂停策略，验证去重后接纳，返回公共状态。
5. 本地已关注和公共采集分别显示，超时先对账，失败不删除个人关注。
6. 取消只影响本地，公共采集按管理员策略继续。

### 5.2 本地发现与服务器跟踪协作

1. 用户配置本地 Cookie，输入UP主并分页扫描当前可见视频。
2. 历史候选默认不选；用户选择部分视频或一键添加全部。
3. 先保存本地关注，必要时持久化公共采集申请；仅向服务器提交目标标识，合作投稿的来源 UP 不作为真实作者依据。
4. 服务器公开查询并校验，接纳后加入共享跟踪；仅本地可访问的候选保留本地状态并说明原因。
5. Agent 不开启本地周期跟踪；将来如有自动规则，放在服务器可采集能力内。
6. 服务器持续采集已接纳目标，客户端按需读取历史，用户独立选择本地视频下载；评论与弹幕留待后续。

服务器自身的公开发现可作为补充入口，不依赖本地 Cookie，也不替代本地登录态发现。

### 5.3 服务器发现视频异常

1. 某个视频本次检查无法访问。
2. 系统保存观测结果，并判断是否需要重新确认。
3. 在缺少充分证据时，标记为疑似异常。
4. 多次有效检查满足规则后，记录确认不可访问事件。
5. 公共页面展示最后确认正常时间和首次异常时间。
6. 提供公共事件，由客户端按本地关注过滤通知。

### 5.4 Agent离线与恢复

1. Agent离线，公共监控服务照常运行。
2. 服务端持续生成并保存视频变化事件。
3. 用户重新启动Agent。
4. Agent 读取本地关注，按标识查询公共详情和历史，恢复待确认采集申请。
5. 恢复用户已提交的扫描与下载，不自动启动长期平台采集。
6. 公共采集确认后更新服务器状态；私人关注以本地为准，缓存可清理，任务进度需保存。
7. 后续如接事件同步，再在本地事务中保存事件、任务和游标；下载不阻塞同步确认。

## 6. 非功能需求

### NFR-001：可靠性

- 事件一经成功提交，应具备持久化能力。
- 关键业务写入具有事务性。
- 系统重启后能够恢复未完成的监控及同步任务。
- 支持至少一次事件投递和客户端幂等处理。

### NFR-002：可扩展性

- 新增用户不应按相同比例增加重复监控请求。
- 监控执行器与业务API逻辑解耦。
- 数据获取实现应通过统一Provider接口接入，以便更换或扩展合法数据来源。

### NFR-003：安全与隐私

- 服务器不持有平台 Cookie、私人关注列表、下载记录和文件。
- 公共 API 只返回允许公开的资料，管理日志、凭据和管理命令不属公共数据。
- 远程使用 HTTPS，本地 API 保留会话、Host/Origin 和 CSRF。
- 采集申请限制大小、批次、并发、频率及全局目标预算，无账号不等于无限制写入。
- 可选访问凭据能撤销，普通申请与全局管理权限分开。
- 日志最小化且不泄漏凭据；目标访问仍有操作痕迹，不宣称匿名。
- 不同使用者隔离本地实例和目录；共享实例需真正的本地权限与存储隔离。
- 用户自选云盘与公共跟踪服务器区分；Agent 上传前加密私人备份，默认排除敏感凭据，密钥不随备份明文上传。恢复先校验并保留回滚能力。

### NFR-004：可观测性

服务端应记录：
- 当前监控目标数
- 最近成功监控时间
- 本次监控结果
- 任务错误及重试次数
- 新增视频和状态事件数
- Agent同步失败情况

### NFR-005：性能

初期面向个人开发和小规模用户群体设计。

并发量、监控周期、日均请求量、状态检测延迟及历史数据容量，需要在确认数据源许可和完成原型压测后制定可执行的指标。

不得为了达到性能指标而突破平台规定的访问频率或权限限制。

### NFR-006：数据保留

公共历史记录仅在合法、必要且符合授权范围的条件下保存。

本地关注、文件与任务由本地保留策略管理；公共历史、服务日志和必要访问控制记录由服务器独立管理，并提供适用的更正及删除机制。服务器不保存私人订阅，个人取消关注不删除公共数据。

## 8. 系统级验收场景

### AC-001：私人关注与公共目标去重

两个 Agent 各关注同一 UP，各保留自己的私人列表；服务器不创建两条个人订阅，只维护一个公共目标。并发或重复申请不创建重复任务，也不反复平台即时查询。

### AC-002：用户离线时仍然追踪

给定全部Agent均处于离线状态。

当公共监控发现视频状态变化时，服务端仍应记录事件并更新历史查询结果。

### AC-003：离线事件补偿

给定用户Agent已经离线，并且服务器生成了多条新事件。

当Agent重新连接时，应能够增量获取未处理事件；重复获取不会生成重复任务。

### AC-004：异常状态判断

给定某视频此前可以正常访问。

当一次检查因为网络超时失败时，不应立即确认视频已下架。

### AC-005：视频文件隔离

给定Agent成功保存了一个有权备份的视频。

公共服务器只能收到选定的公共跟踪标识及必要的请求信息，不应收到平台 Cookie、视频文件、媒体分片、评论正文或本地文件路径。

### AC-006：多人公共数据与本地隔离

A、B 各用自己的 Agent 和目录。A 取消本地关注不改变 B 的列表，不停止公共采集；公共服务器没有个人订阅读取接口。Cookie、下载和偏好留各自设备，普通客户端不能调用全局管理命令。共享实例另行验收本地登录与存储隔离，不能仅靠档案选择。

### AC-007：历史记录真实性

给定系统从10:00至12:00未检查某个视频，并在12:00首次发现视频不可访问。

系统不得宣称视频恰好在12:00被删除，应显示首次发现异常的时间及最后正常观测时间。

### AC-008：按需发现与服务器跟踪分离

多页候选默认未选，一键添加全部覆盖未加载页；本地保存后显示已关注，公共申请逐项确认前不显示跟踪成功。关注 UP 不自动关注全部历史视频或下载。关闭 Agent 后服务器继续采集，Agent 不运行本地周期跟踪，恢复扫描或下载不产生另一套长期指标历史。

### AC-009：离线补发现与双向断连

用户恢复未完成的按需扫描或重新发起扫描时，应覆盖需要的后续页并去重，不能只读最新一页后误报全部；Agent 不自动启动周期补扫。服务器继续采集此前已知目标，断连时待确认操作保留本地，重连后先对账再幂等提交。已消失或缺乏观测的数据明确标为缺失。

### AC-010：凭据与本地任务隔离

受限服务访问凭据失效不影响本地有效 Cookie 的独立任务；B站 Cookie 失效不影响按服务策略读取公共历史。下载及未来评论/弹幕任务重启可恢复，不重复标记完成，文件始终留在本地。

### AC-011：本地档案管理与个人存储（按阶段验收）

数据管理可在不连接公共服务器时导出/恢复私人档案；默认备份无 Cookie、云盘密钥和媒体，恢复不自动执行任务；错误密钥、损坏备份、异机路径不匹配、断网和并发备份不破坏已有数据；清理本地、删除云端历史和公共停采相互独立，见 [数据管理验收](client-data-management.md#实施顺序与验收)。

## 9. 外部依赖与风险

| 风险 | 影响 | 处理原则 |
|---|---|---|
| B站自动化访问权限限制 | 核心功能可能无法公开运营 | 优先官方授权接口或合法合作数据源 |
| 授权接口能力不足 | 无法完整发现任意UP主投稿 | 缩小MVP支持范围，不通过绕过限制补齐 |
| 视频状态结果不准确 | 导致错误下架判断 | 多次确认、保留观测依据 |
| 个人信息与评论保护 | 产生隐私和版权风险 | 限制数据范围，支持纠错和删除 |
| Agent离线 | 不能完成及时备份 | 明确产品不保证完整备份 |
| 本地账号凭据泄漏 | 用户账号安全受损 | 凭据本地化、安全存储、最小授权 |
| 任务规模扩大 | 增加数据库和调度压力 | 去重、限流、可观测性和容量规划 |

## 10. 后续版本规划

**V0.1：需求验证与最小闭环**

在现有服务端查询、持久化与观察台基础上，补齐公共记录、受控采集申请、私人本地关注、Agent 发现和下载闭环；使用Mock Provider验证分页、状态事件、断连与任务恢复。

**V0.2：合法真实数据接入**

在现有公开查询之外，验证本地 Cookie 可用的发现能力，完善真实平台接入；按 [客户端阶段](../client/README.md#实施阶段与验收) 扩展本地视频下载，后续再接入本地评论保存。

**V0.3：用户体验完善**

完善历史时间线、通知、可配置监控策略和客户端任务管理；在本地档案备份基础上接入用户自选存储，逐步扩展自动备份及多设备同步，不要求公共跟踪服务器托管用户账户。

**V1.0：可公开使用版本**

完成必要的合规、安全、稳定性、部署、监控及用户数据管理要求后正式发布。

7. 本地备份在合法授权范围内，第一版具体支持哪些内容及文件格式？

## 12. 文档维护原则

- 本文档负责定义产品行为、边界和验收条件。
- 技术栈、数据库表结构、接口参数和部署架构由独立技术设计文档规定。
- 需求变更应先修改PRD，再同步技术设计、任务及测试。
- 已实现功能应能够追溯到需求编号。
- 对尚未确认的外部授权能力，不得在技术方案中默认为已经具备。
