# 当前资料本地查询与服务器历史读取

## 职责

当前名称、头像/封面、视频发布时间、播放量与粉丝数由本地 Agent 查询 B站。服务器继续采集和保存已知目标的历史版本与日指标，为客户端提供历史变化；本地平台获取失败或缺失字段时，才读取服务器已有资料兜底。兜底不触发服务器实时上游查询。

UP/视频库、本地库中的卡片刷新、UP 详情已关注视频以及当前详情使用相同来源规则。Cookie 留在 Agent，经 scanner 传入固定 B站端点，不进入公共服务器请求、浏览器响应或日志。服务器跟踪申请与后台核对仍独立运行，本地取消关注不停止公共采集。

```text
+---------------------------+
| Browser: cards / detail   |
+---------------------------+
              | local session HTTP
              v
+---------------------------+
| Agent: current + history  |
+---------------------------+
       | current       | history / explicit fallback
       v               v
+------------------+  +----------------------------+
| Bilibili API     |  | Server :8181               |
| local Cookie     |  | samples / versions / IDs   |
+------------------+  +----------------------------+
```

箭头表示请求，响应沿原路径返回。图片文件由浏览器直连白名单 CDN，两个服务都不代理媒体文件。

## 当前资料

[bilibili/metadata.go](../client/agent/internal/bilibili/metadata.go) 的 `Current` 复用仓库原有适配器已经使用的两个网页端点：`/x/web-interface/card?mid=...` 和 `/x/web-interface/view?bvid=...`。它们可能因登录态、风控或端点变化而失败；不是新增的官方稳定 API 契约。本轮使用固定 HTTP 响应回归，没有用真实 Cookie 或真实 B站响应完成联调。

适配器验证返回 UID/BV 身份、名称、非负指标及发布时间；缺失指标保留 nil，真实零值保留 0。只访问固定 HTTPS 主机，禁止重定向。当前资料请求共享 150ms 启动间隔与最多 4 个在途请求。分页扫描仍沿用原有显式启动、Cookie 和进度规则，不因为展示卡片而自动枚举全部投稿。

[library/current.go](../client/agent/internal/library/current.go) 合并同一目标的在途当前资料请求，使用 1 分钟缓存与最多 2000 项内存索引；关注摘要已持久化，重启后仍可复用 TTL 内的 B站资料。429/受限错误进入至少 1 分钟冷却，避免每个目标重复撞风控。当前资料和历史观测分别使用 `metadata_at` 与 `observed_at`，不能由当前粉丝/播放量减历史首点冒充服务器记录的变化。

正常 Agent 在 [main.go](../client/agent/cmd/agent/main.go) 向 library 注入 scanner 的 `CurrentSource`。省略可选源的库构造方式保留给旧接入方；命令入口始终启用本地优先。无 Cookie 时可以尝试公开资料，失败再兜底，不为浏览卡片强制登录。

## 整页批量变化

本地关注先显示摘要，再刷新当前页最多 24 个不同目标。每轮总预算 30 秒，本地当前资料阶段最多 12 秒、最多 4 个工作者；之后只发一次服务器批量历史请求：

```json
{"kind":"video","ids":["BV17x411w7KC","BV1oa41137pj"],"days":7}
```

路径为 `POST /api/metrics/batch`。只有本地失败或缺少指标/图片的 ID 才出现在可选 `fallback_ids` 中；这些 ID 必须属于 ids，不允许重复或超限。入口沿用进程共享限流、JSON 64 KiB 上限、来源校验和 8 秒查询预算。

成功本地获取的一页在服务器执行 **1 次限定 ID 的指标查询**；存在兜底项时再加 **1 次限定 ID 的资料查询**。不会对每张卡片查询目录总数、投稿汇总或完整详情。`fallback_ids` 返回的资料只填补本地缺失字段，不能覆盖已经成功获取的本地名称/指标。

[storage/client_history.go](../backend/internal/storage/client_history.go) 的 `MetricsBatch` 仅访问指定平台、类型、指标、ID 集合与近 7 个 UTC 日窗口；每个目标最多最新 5000 点，缺失返回空数组。Agent 使用首末有效样本计算增量，允许负增长，少于两个样本显示未知；超限时不展示误导的完整窗口增量。源时间范围保存在 growth_from/growth_to 中。

历史失败时仍保存本地成功资料，保留旧历史并提示；两种来源都失败时保留旧缓存。同步返回前核对服务器代际与原关注身份，取消后重关注、切服后切回不会接纳旧请求写回。后台核对只负责任务状态；核对成功后按类型合并本轮最多 3 项的资料刷新，不恢复逐项目录/完整详情读取。

切换服务器时可以保留纯B站来源的当前资料，但剥离旧服务器的版本、指标、任务确认和历史缓存；服务器兜底字段不会冒充独立的本地资料被带到新服务器。

## 公共库枚举

公共库无法仅凭私人关注知道服务器收录了哪些目标，因此仍需服务器枚举身份。新 Agent 的目录和总览请求带 `projection=identity`，[CatalogIdentity](../backend/internal/storage/catalog_identity.go) 普通分页只从目标当前表计数和读取 ID、版本指针、历史观测时间；不读任务、版本 payload 或 UP 投稿汇总，也不关联指标窗口。

公开搜索使用服务器已记录的名称/标识筛选，排序基于服务器最近记录；展示的当前资料再由本地补齐。热门排序确实需要对应类型的历史增量，单独按该类型的近 7 日采样排行，未知值排末尾。它仍覆盖完整候选集，不只重排当前页。公共 UP 库不提供私人“本地视频播放合计”排序或投稿时间排序；这些仅适用于本地结果集。

旧调用方不带 projection 时沿用原有 Catalog；后台观察台的原查询与业务协议保留。新的本地优先 Agent 不使用旧目录响应来刷新每个关注项。

## 当前详情和历史版本

`GET /api/history/{type}/{id}?days=7|30|90|all&page=...` 只读取轻量历史头、版本分页和日指标，不读取当前图片、投稿聚合或任务状态；正常详情为 4 次 SQL。明确 `seq=N` 时只查询该版本快照，为 1 次 SQL，不重复取趋势和版本目录。

当前详情把本地资料与服务器历史组合；服务器没有历史时仍可显示本地获取的当前资料，并明确历史暂无记录。默认 30 日第一页的历史缓存继续用于离线回退，非默认范围不能冒充默认离线历史。选中旧版本只影响快照/差异区，不能覆盖当前卡片摘要、头像或当前数量。

`GET /api/metadata/{type}/{id}` 是单目标资料兜底。它和批量兜底共用 `MetadataBatch`：仅按目标读取当前字段与所选图片，没有目录计数、指标窗口、任务或投稿聚合。不存在返回 `DETAIL_NOT_RECORDED`，无快照返回 `SNAPSHOT_NOT_FOUND`，内部故障保留 HTTP500。

当前图片直接使用资料返回的白名单 URL；`seq=0` 的图片解析也先本地后兜底。明确历史版本则使用历史专用入口和版本缓存，不使用当前 B站图片冒充历史图片。

## UP 本地汇总

用户确认 UP 播放合计为 **本地已关注视频** 的最近缓存播放合计，不代表服务器已记录范围或 B站全部投稿。[local_stats.go](../client/agent/internal/library/local_stats.go) 一次遍历本地关注后按作者分组，不发服务器请求；视频主作者缺失时可使用明确扫描关联。

近 7 日投稿数、最近投稿时间也只使用这些本地已知视频的发布时间。计数随取消/新增关注与 UTC 窗口推进而变化；播放总数有未知项或溢出时保留未知，发布时间不完整时不把新投稿数伪装成完整的零值。空的已关联关注集合为真实零项。汇总读取本地最近资料，刷新视频资料后会更新，不隐式扫描作者全部投稿。

本地排序仍在完整本地结果集上进行后分页；只有当前页被刷新时，其他页仍可能使用较旧缓存。公共热门排序依赖服务器历史排行，当前本地数量不会被当成全站实时排行依据。

### 服务器侧隔离基准

在 Windows/amd64、Intel i7-14650HX、Go 1.26 的同一临时夹具（128作者、1024视频、8064条7日采样）运行：

```powershell
go test -run '^$' -bench '^BenchmarkClientPageHistory$' -benchtime=300ms -count=3 -benchmem ./internal/storage
```

| 一页18项的服务器读取 | 三轮耗时中位数 | Go分配/次 |
|---|---:|---:|
| 旧逐项目录摘要，18次Catalog | 114.839 ms | 约356.5 KB |
| 新一次目标限定历史批读 | 0.373 ms | 约21.8 KB |

新方案把当前资料的获取移到了本地，因此两行不是返回完全相同内容的 SQL 替换；它比较的是职责调整前后的服务器工作。未包含本地B站请求、网络往返、限流、页面渲染或真实 VM 并发，不能将此比例当成页面加速倍数或实际容量承诺。

### 远程 VM 整页容量实测

2026-11-19 在一台 2 vCPU、3.8 GiB 内存的 Ubuntu VM 上，以提交 `e2124b3` 的 Linux/amd64 二进制启动隔离实例。测试实例使用停机状态远端数据库的副本，不修改原数据库或远端仓库；公共端口为临时的 `18181`，管理端只监听回环。测试结束后服务、数据库副本和临时二进制均已删除。

数据库包含 90 个作者和 2766 个视频。请求分别为 `GET /creators?page=1&projection=identity` 与 `GET /videos?page=1&projection=identity`，每次返回第一页 18 项，响应体约 5.26 KiB。负载发生器位于 VMware 宿主机，复用 HTTP/1.1 连接；每个响应同时校验 HTTP 200、`ok=true`、18 项结果和有效总数。每档持续 10 秒，场景间冷却 2 秒；`BHT_API_RPS` 临时提高到 10000，以测处理容量而不是默认限流策略。

| 目录 | 并发 | 成功页/秒 | P50 | P95 | P99 | 最大值 | 失败 |
|---|---:|---:|---:|---:|---:|---:|---:|
| UP 库 | 1 | 874.19 | 0.731 ms | 4.779 ms | 6.321 ms | 28.822 ms | 0 |
| UP 库 | 4 | 2469.93 | 1.479 ms | 2.786 ms | 3.881 ms | 11.595 ms | 0 |
| UP 库 | 16 | 2371.22 | 5.939 ms | 13.864 ms | 19.054 ms | 45.863 ms | 0 |
| 视频库 | 1 | 505.18 | 1.857 ms | 2.530 ms | 3.442 ms | 7.575 ms | 0 |
| 视频库 | 4 | 634.62 | 5.929 ms | 10.541 ms | 13.364 ms | 29.098 ms | 0 |
| 视频库 | 16 | 604.47 | 22.658 ms | 59.508 ms | 80.559 ms | 145.591 ms | 0 |

另以 8 秒负载和同步的 10 秒 `pidstat` 复测 4 并发资源：UP 库约 2343.68 页/秒，服务进程平均使用 102.90% CPU、约 23.6 MiB RSS；视频库约 615.09 页/秒，平均使用 70.50% CPU、约 23.7 MiB RSS。两组磁盘读取均为 0，平均写入约 0.4 KiB/s，数据已由操作系统页缓存提供。

4 并发已接近这份数据库和 VM 的有效平台；提高到 16 并发没有增加吞吐，只增加排队延迟。视频目录需要在更多候选记录中筛选和排序，吞吐低于 UP 目录；结合单连接 SQLite、无磁盘读取、低内存占用和并发平台现象，瓶颈更接近目录 SQL 的串行执行，而不是内存容量或物理磁盘读取。这是测量后的推断，不是 SQL profile 的直接归因。

该结果只覆盖服务器返回一页轻量身份目录，不包含 Agent 随后的批量历史请求、本地 B站 API、浏览器渲染或后台采集。生产默认 `BHT_API_RPS=20` 时，接纳吞吐仍会先受全进程限流约束；上述页/秒用于说明取消逐项目录聚合后的处理余量，不能直接换算成在线用户数。
