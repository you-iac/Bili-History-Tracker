# 跟踪失败阶梯降频

- 创建时间：2026-11-20 17:15（Asia/Shanghai）。
- 状态：待实施；本计划只记录设计与决策点，不含代码改动。

## 目标

服务器跟踪对每个目标按固定周期（默认 3 小时）查询，无论成功与否。已消失或长期不可达的视频会以全速持续请求：观察台当前可见「上游未找到，连续 53 次」「访问受限，连续 56 次 / 59 次」「上游未找到，连续 66 次」等目标，仍在每 3 小时触发一次查询。这些请求对平台是纯噪声，占用入口配额，也让真实异常的告警被淹没。

本计划让持续失败的目标按阶梯降低查询频率，直到每周一次；目标恢复可查询后自动回到用户设定的周期。

## 现状（代码事实）

- `backend/internal/tracker/tracker.go`：`DefaultInterval = 3 * time.Hour`；调度使用 `target.IntervalSeconds`，由 `MarkTargetRun(ctx, target, now, next)` 写入下一次执行时间。
- `backend/internal/storage`：`targets` 表已有 `failure_count`、`last_failure_at`、`failure_reason`、`recovered_at`、`last_result`；`failure_count` 在结果非 `ok` 时 +1、成功时归零（`dashboard.go:67-70`）。观察台的「连续 N 次」即此字段。
- `backend/internal/source/source.go`：错误分类为 `invalid_input`、`not_found`、`rate_limited`、`upstream_failure`。
- 入口限流 `BHT_API_RPS` 是**全局**配额，与单目标无关。

## 设计

### 1. 退避阶梯

按连续失败次数选择下一次执行间隔，基数取目标自己的 `interval_seconds`（用户设定），阶梯为倍率：

| 连续失败次数 | 退避倍率 | 3 小时周期下的实际间隔 |
|---|---|---|
| < 3 | 1× | 3 小时 |
| 3–5 | 2× | 6 小时 |
| 6–9 | 8× | 24 小时 |
| 10–14 | 24× | 72 小时 |
| ≥ 15 | 56× | 168 小时（1 周） |

上限固定为 1 周。退避只影响 `next_run_at` 的计算，**不修改** `targets.interval_seconds`，避免把临时降频写进用户设置。

### 2. 按错误类型分派

四种失败不能等同处理：

- **`not_found`**（上游未找到）：目标很可能已删除或下架 → 正常走阶梯退避。
- **`rate_limited`**（访问受限）：这是**我方**被平台限流，属全局问题，不是目标消失。逐目标退避会把「全局过载」记成「一批坏目标」，恢复后仍要干等。正确处理是全局节奏控制（`BHT_API_RPS`、并发上限、`Retry-After`），目标自身最多做短退避（≤ 1 小时），且**不计入**死亡阶梯。
- **`upstream_failure`**：平台抖动或网络错误 → 短退避（15–30 分钟）重试，不计入死亡阶梯。
- **`invalid_input`**：配置错误，标记为需人工处理，不做自动重试。

### 3. 恢复

任何一次查询成功：`failure_count` 归零、`recovered_at` 记录，下一次执行回到用户设定的基础周期。这是现有 `dashboard.go:70` 的行为，退避不需要额外状态。

### 4. 手动旁路

管理页「立即刷新」与 `/targets/run` 必须无视退避立即执行一次，并照常更新失败计数。降频只影响自动调度。

### 5. 可观测

观察台与公共 API 应显示「已降频：下次 X 时间（原周期 3 小时）」，否则用户会把降频误判为调度故障。`GET /api/targets/status` 增加退避字段。

## 决策点（实施前确认）

1. **首次降频阈值取 3 次还是 10 次？** 按 3 小时周期，10 次意味着 30 小时后才开始降频，期间仍要打 10 次无效请求。
2. **`rate_limited` 是否参与死亡阶梯？** 本计划建议不参与，只做短退避，并单独统计全球限流比例。
3. **1 周上限是否足够？** 是否需要「连续失败超过 N 天自动标记为失效、停止自动查询」的终态。
4. 是否需要人工「恢复全速」入口。

## 实施步骤（后续）

1. `storage` 补充调度路径所需的 `failure_count` 与 `failure_reason` 读取（若尚未读取）。
2. `tracker` 计算 effective interval 并写入 `next_run_at`；`interval_seconds` 保持不变。
3. 按错误类型分派退避策略；`rate_limited` 接入全局节奏控制。
4. 观察台与公共 API 暴露退避状态。
5. 补测试：阶梯边界、成功清零、手动刷新旁路、限流不累加死亡计数。

## 验收

- 连续 `not_found` 的目标在达到阈值后间隔按阶梯增长，最终稳定在 1 周，期间无报错。
- 一次成功后立即回到用户设定周期，观察台显示恢复。
- `rate_limited` 不增加死亡计数，短退避后恢复。
- 「立即刷新」无视退避生效。
- 观察台能看出某目标处于降频状态，而不是看起来像调度坏了。

## 风险

- 退避过激会让真正恢复的视频延迟一周才被重新发现；阶梯与上限需可配置。
- 若不区分 `rate_limited`，一次限流风暴会把大量目标打入长期退避，恢复期数据出现长时间空洞。
